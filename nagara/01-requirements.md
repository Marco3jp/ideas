# 01. 要求整理

Issue #32 本文・コメントおよび本タスクの依頼文から、要求を抽出して整理する。

## 1. ユーザーストーリ

- 起きている時間に、自室で、自分（=作者）が
- 音楽でも「ちゃんと見たい動画」でもなく、選ぶ手間ゼロで、
- なんとなく耳を傾けると意味がある、くらいの距離感の声を
- 流し続けてほしい。

## 2. 利用環境（前提条件）

| 項目 | 前提 |
|---|---|
| 視聴端末 | 自宅の Windows PC（メイン） |
| 動かす場所 | 同 LAN 上の Linux PC でも、視聴用 Windows PC でも可 |
| ネットワーク | LAN 内に閉じてよい。インターネット越しの公開は不要 |
| 起動運用 | 「起動が面倒」は嫌。Linux 常駐なら起動の手間が消えるのでむしろ歓迎 |

> 結論として「**Linux PC で常駐**」を第一候補、「Windows 単体」を退避ルートとする。
> （理由は [03-mvp-design.md](./03-mvp-design.md#デプロイ戦略) で述べる）

## 3. 機能要求（Issue 本文＋本タスク依頼）

### 3-1. キュー管理システム

- バックエンドで再生キューを生成し、フロントから順次消化する。
- ドメイン（YouTube／Podcast 等）ごとに以下の操作インターフェイスを統一して持つ。
  - **ロード**（次のエピソードを準備）
  - **再生**
  - **一時停止**
  - **見終わり検知**（シークが最後まで動いたこと）
  - **再生速度コントロール**
  - **フルスクリーン**
  - **コメントスクリーンありフルスクリーン**（コメント描画レイヤーをかぶせるフルスクリーン）

### 3-2. コンテンツ管理

- 投稿者・チャンネル・番組の登録／削除。
- チャンネルごとの並び替えポリシー（新着優先 / 古い順優先）。
- エピソード単位の Disable（「このエピソードはまだ流したくない」用）。
- 正規表現による Disable（「定期配信のXXXは流さないでほしい」用）。
- ミュートリスト（投稿者・動画・キーワード）。

### 3-3. 視聴履歴

- 再生開始・完了を記録する。重複再生の排除に使う。
- 「途中まで」状態も保持できる方が望ましい（必須ではない）。

### 3-4. 自動キューイング（普段見る投稿者の管理）

- 登録された投稿者の新着リストを束ねて、自動でキューに積む。

### 3-5. ザッピング機能（おすすめ／クルーズ的なやつ）

- 数分経ったら自動で次に行く（ニコニコクルーズ的）。
- 行く前に少しだけ「続き見る？」を出して、続きを見ることもできる。
- 「おすすめ的な動画をキューに入れる」枠も将来的にほしい。

### 3-6. その他リクエスト

- 任意の User-Agent を指定できる仕組みもほしい（コメント由来）。

## 4. 非機能要件

### 4-1. ネットワーク

- LAN 内アクセス前提。
- 認証は MVP では不要（「自宅 LAN 内」が物理的な防壁）。
- インターネットに公開しない。

### 4-2. 運用

- 「起動が面倒」を避けるのが最優先要件のひとつ。
  - Linux 常駐 → systemd で起動する想定。手動起動は要らない。
  - Windows で動かす場合 → Docker Desktop 起動 or `npm run start` を毎回打つことになり、
    要件「起動が面倒なのは避けたい」を悪化させる。よって優先度は低い。

### 4-3. データ保持

- 視聴履歴・登録チャンネル・フィルタ設定はローカルファイルに永続化される。
- 単一ユーザー想定なので、マルチテナントや権限制御は不要。

### 4-4. 重複排除

- Issue 備考にある「時間に対して 1 倍以上の音声量が必要」を満たすため、
  重複再生を抑える仕組み（履歴ベース）が前提。
- 言い換えると、登録するチャンネル数が少ないと破綻するので、
  運用上は「登録ソースを増やす UI が手早く使えること」が機能要件として効いてくる。

## 5. スコープ管理（MVP の境界）

依頼文の「まずミニマムに作ってから考える」を厳守するため、
**MVP に入れるもの／入れないもの** をここで明示しておく。

| 項目 | MVP に入れる？ | 補足 |
|---|---|---|
| YouTube 新着取得（公式 RSS / API キー不要） | ○ | `feeds/videos.xml?channel_id=...` を採用 |
| Podcast RSS 取得 | ○ | `<enclosure>` ＋ `<itunes:duration>` 採用 |
| YouTube 埋め込み再生（IFrame Player API） | ○ | 公式 API、`onStateChange` で見終わり検知 |
| Podcast 音声再生（`<audio>` 直） | ○ | RSS の `<enclosure url>` を `src` に |
| キュー自動生成（チャンネル間ラウンドロビン） | ○ | 履歴で重複排除 |
| ザッピング（タイマーで次へ） | ○ | 「続き見る？」オーバーレイも MVP に含める |
| エピソード単位 Disable | ○ | 一覧 UI からトグル |
| 正規表現フィルタ | △ | データモデルだけ用意。UI は後 |
| ミュートリスト（チャンネル・キーワード） | △ | 同上 |
| Radiko 連携 | × | 認証フロー実装が重い。後で検討 |
| TVer 連携 | × | 公式埋め込みなし。スクレイピング保守が辛い |
| 任意 UA 設定（プロキシ経由） | × | RSS 取得時のみ環境変数で渡せれば最低限 |
| コメントスクリーン付きフルスクリーン | × | コメント取得元自体が未確定 |
| 古い順優先ポリシー | △ | データモデルだけ用意、デフォルトは新着順 |
| スマホ対応 | × | Windows ブラウザのみ |
| 認証 | × | LAN 限定 |

> △は「データモデル／API のフィールドは確保するが UI は後回し」の意。
> 後から追加するときにスキーマを壊さないために、この区別を意識して設計する。

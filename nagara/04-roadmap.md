# 04. MVP 後のロードマップ

MVP（[03-mvp-design.md](./03-mvp-design.md)）を実際に運用してみて、
不便だと感じたものから順に潰していく。**事前に作り込まない**。

ここに並べた項目は「事前に作る予定」ではなく
「**作るとしたらこの形が筋が通る、という当たりだけ付けたメモ**」。

## 優先度: 高（MVP 直後に手を出しそう）

### R1. Tier 2／Tier 3 のサイト別フィージビリティ調査

MVP のコードができた段階で、普段見るプラットフォームを 1 サイトずつ通して確認する:

- yt-dlp `-j` で `formats[]` がどう返るか（DRM の有無、HLS か progressive か）。
- HLS プロキシ越しに `hls.js` で再生したときに CORS／トークン期限がどう振る舞うか。
- Tier 3 が必要なサイトでは、コンテンツスクリプトでの `<video>` 取得セレクタを記録する。

調査結果は `nagara/05-feasibility-matrix.md`（仮）に表で残す。
新しいサイトを足すときの事前チェックリストとして機能する。

### R2. 共有メニュー連携の強化

補助 UI への投入導線を強化する。

- 補助 UI を PWA 化済みの状態から、`registerProtocolHandler` 等で OS の共有先候補に出すようにする。
- ブラウザ拡張に「現在のタブの URL を nagara キューへ送る」ボタンを足す
  （Tier 3 用の拡張に機能を追加する形）。
- 複数 URL の一括投入（補助 UI の入力欄を多行対応）。
- ペースト時の自動 URL 検出（「https://...」を含む文章を貼っても URL 部分だけ拾う）。

### R3. 履歴の重複検出と "再投入抑制" の任意化

- `history` には残っているので、UI 側で「最近 N 日に流したやつは薄く表示」を出すだけで足りる。
- 強制的に弾くのではなく、ユーザに見せて選ばせる。

### R4. 進捗保存（途中スキップ時の `progress_seconds` の活用）

- 履歴に保存している `progress_seconds` を、再投入時の「続きから」開始に流用する。
- `load(item, startAtSeconds)` のインターフェイスは MVP で用意済み。

### R5. キューのインポート／エクスポート

- JSON でキューと履歴を吐ける／読めるようにする。
- マシン引っ越し、別端末との同期。

## 優先度: 中（手動キューの運用感が見えてから）

### R6. 投稿者・チャンネル登録（自動キューイングの前段）

- `channels` テーブルを足し、`items.channel_id` を NULL 許容で追加する。
- YouTube は `https://www.youtube.com/feeds/videos.xml?channel_id=<UC...>`（API キー不要）。
  Podcast は RSS。
- 入れる粒度の判断は **手動キュー運用の中で「これは毎回貼るのが面倒だ」と感じた投稿者だけ** 登録する。

### R7. 自動キューイング（おすすめ／クルーズ的なやつ）

- R6 の投稿者登録と MVP の履歴データが揃って初めて意味のある自動化ができる。
- 想定アプローチ:
  - 「明示的に登録した投稿者の新着」を別キュー（"オートキュー"）として持ち、
    手動キューが空になったら流す。
  - ユーザが手動キューに積んだものは常に最優先。

### R8. ザッピング機能（自動次へ＋続き確認）

- R7（自動キューイング）と組み合わせて初めて意味のある機能。
  自動で積まれた動画を一定時間で送る「クルーズ」体験に必要なため、R7 とセットで実装する。
- 設定 `zapping_timeout_seconds` で有効化、`zapping_grace_seconds` で猶予秒数。
- 「続けるか／切るか」のオーバーレイは MVP の割り込み UI と近い表現で実装できる。

### R9. 正規表現フィルタ・キーワードミュート

- R6 の投稿者登録機能が入ってからでないと「フィルタ対象」がそもそも存在しない。
- `filters` テーブルを足して、自動キューイングと手動キューの両方に適用する。

### R10. Radiko 連携

- Tier 2 の枠組みに乗せる（バックエンドで auth1/auth2 → HLS → プロキシ → フロントは `hls.js`）。
- 「ながら聴き」用途と相性が良いので、需要が出たら優先度を上げる候補。

### R11. Tier 3（Chrome 拡張）の対応サイトホワイトリスト拡充

- MVP 時点で TVer 用の URL 判定ロジックは入っている。
- 運用しながら他に「ネイティブ埋め込み NG ＋ DRM ＋ 公式プレイヤーは autoplay 連鎖が効く」
  サイトを足していく。
- 各サイトでコンテンツスクリプトの `video` セレクタが微妙に違うため、
  `extension/content/site-rules/<host>.ts` のようにサイトごとの差分を追加する形にする。

### R12. Chrome 拡張の Chrome Web Store 公開

- MVP では開発者モードでの読み込み運用。
- 自分以外も使うようになったら CWS 申請。プライバシーポリシー整備が要る。

### R13. コメントスクリーン付きフルスクリーン

- 取得元の問題が大きい。
  - YouTube ライブのリプレイチャットは API キー＋Quota が痛い。
  - ニコニコ過去コメントは非公式 API 利用＋規約注意。
- 描画側は `<canvas>` を Tier 1（IFrame）／Tier 2（hls.js）の player の上にかぶせるだけで素直。
- Tier 3（拡張モード）は別タブ側なので、コメントオーバーレイをかぶせるには
  コンテンツスクリプトで `<canvas>` 注入する追加実装が必要。

## 優先度: 低（必要性が出てから）

### R14. 認証 / アクセス制御

- 自宅 LAN を出る運用が出てきたら Basic 認証または Cloudflare Tunnel 等を前置する。

### R15. メイン UI のスマホ対応

- メイン UI もスマホで動かしたくなったら、レイアウトを縦長対応にする。
- Tier 3 はモバイル Chrome では拡張未対応のため、スマホでは Tier 1／Tier 2 のみとなる。

### R16. プレイヤー Adapter の追加

- 新しいソースを足すときは `PlayerAdapter` の実装を 1 個増やすだけで済むよう、MVP で抽象化済み。
- 想定追加先: SoundCloud／Spotify Embed／Vimeo／自前 mp3 ホスティング 等。
- ほとんどは Tier 1（公式埋め込み）か Tier 2（yt-dlp）で吸収できるはず。

### R17. 統計ダッシュボード

- 「今日のうちに何時間流したか」「ジャンル比率」などを可視化。
- `history` テーブルだけで成立するので追加スキーマ不要。

## 優先度: 別軸（運用・周辺）

### R18. systemd / 自動起動の整備

- インストールスクリプト `scripts/install-systemd.sh` を整備。
- `journalctl` でログを集約。

### R19. バックアップ

- SQLite ファイル 1 個なので `cp` と `tar` で十分。
- `data/` 配下を週次でホームディレクトリの別フォルダに丸コピー。

### R20. テストとモック

- MVP では手動 E2E（自分で触って確認）で十分。
- メタ取得・yt-dlp 呼び出しは外部依存があるので、ロジック関数だけ単体テストし、
  実フィードはサンプル XML/HTML/JSON をリポジトリに同梱する。

---

## やらない（明示的に除外）

- マルチユーザー化／権限制御
- リコメンドのために大きな機械学習モデルを動かす
- クラウドへのホスティング（VPS / Vercel 等）
- SaaS 化

これらは本ツールの意図（自宅で使う／自分用）と方向が違うので、選択肢から外す。

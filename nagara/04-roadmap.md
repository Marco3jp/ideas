# 04. MVP 後のロードマップ

MVP（[03-mvp-design.md](./03-mvp-design.md)）を実際に運用してみて、
不便だと感じたものから順に潰していく。**事前に作り込まない**。

ここに並べた項目は「事前に作る予定」ではなく
「**作るとしたらこの形が筋が通る、という当たりだけ付けたメモ**」。

## 優先度: 高（MVP 直後に手を出しそう）

### R1. 「古い順優先」ポリシーの UI 露出

- データモデルには `order_policy = 'oldest_first'` を最初から入れてある。
- 「最近知った V の昔の配信から流したい」という Issue 要望そのもの。
- UI を出すだけで実装の追加コストはほぼゼロ。

### R2. 進捗保存（途中スキップ時の `progress_seconds`）

- MVP では `skipped` の行に最終位置を入れるだけ。
- 「続きから」UI を増やすときに、この値を読み出して `seekTo` で復元する。

### R3. 正規表現フィルタの UI

- `filters` テーブルは MVP で用意済み。
- 入力欄と検証用の「マッチするタイトル一覧プレビュー」をつけるだけで成立する。

### R4. キュー再構築のリアルタイム化

- 現状はクライアントが `GET /api/queue` を再フェッチする方式。
- 視聴履歴を書いた直後にだけ再取得すれば十分なので、SSE まで持ち込まなくていい。
  ただし「複数タブで開いた時に同期したい」みたいな話が出たら SSE か WebSocket を導入する。

## 優先度: 中（触り込んでから判断）

### R5. ニコニコクルーズ的な「おすすめザッピング」

- Issue でいう「おすすめ的な動画をキューに入れるやつ」。
- MVP の自動クロールと履歴があれば、以下のような単純ロジックで近似可能:
  - 視聴傾向（履歴で `completed` の多いチャンネル）の隣接チャンネルを ` related` っぽく扱う。
  - YouTube の関連動画 API は API キーが要る上に Quota が痛いので、
    まずは「普段見ているチャンネルの未視聴エピソードを優先」程度の実装で十分のはず。
- MVP のキュー生成 SQL に `ORDER BY` の組み替えを足すだけで実現できる。

### R6. コメントスクリーン付きフルスクリーン

- 取得元次第。
  - ニコニコ系コメント: 過去のコメントを取得する非公式 API は存在するが、
    自前運用と利用規約の確認が要る。
  - YouTube ライブチャットのリプレイ: API キー必須で Quota も痛い。
- MVP 時点では仕様未定なので保留。
  実装するなら `<canvas>` でコメント流す層を player の上に被せるだけなので
  描画側は素直。重いのはコメントデータの取得。

### R7. Radiko 連携

- [02-research.md](./02-research.md) §3 のとおり、
  - バックエンドで `auth1` → `auth2` を叩いて `X-Radiko-AuthToken` を取り、
  - HLS プレイリスト＋セグメントの取得もバックエンドプロキシ経由にする
  - フロントは `hls.js` で再生
  という構成になる。
- 認証鍵やリージョン判定の取り扱いは慎重に。
- 音声中心の本ツール用途とは相性がよいので、需要が出たら優先順位を上げる候補。

### R8. TVer 連携

- [02-research.md](./02-research.md) §4。
- 子プロセスで `yt-dlp` を呼び出して m3u8 を抽出する経路が現実的。
- DRM 動画は除外する。
- 「ながら聴き」用途では音声情報量が少ない番組も多いので、
  対象番組をホワイトリスト管理する設計になりそう。

## 優先度: 低（必要性が出てから）

### R9. 認証 / アクセス制御

- 自宅 LAN を出る運用が出てきたら Basic 認証または Cloudflare Tunnel 等を前置する。

### R10. スマホ対応

- レイアウトを縦長対応にすればおおむね動くはず。
- ただし iOS Safari では `<audio>` の autoplay がさらに厳しいため、再生ボタンの導線を増やす必要がある。

### R11. プレイヤー Adapter の追加

- 新しいソースを足すときは `PlayerAdapter` の実装を 1 個増やすだけで済むよう、
  MVP の段階で抽象化しておく（[03-mvp-design.md](./03-mvp-design.md) §6-2）。
- 想定追加先: SoundCloud／Spotify Embed／Vimeo／自前 mp3 ホスティング 等。

### R12. 統計ダッシュボード

- 「今日のうちに何時間流したか」「ジャンル比率」などを可視化。
- 履歴テーブルだけで成立するので追加スキーマ不要。

## 優先度: 別軸（運用・周辺）

### R13. systemd / 自動起動の整備

- インストールスクリプト `scripts/install-systemd.sh` を整備。
- `journalctl` でログを集約。

### R14. バックアップ

- SQLite ファイル 1 個なので `cp` と `tar` で十分。
- 念のため `data/` 配下を週次でホームディレクトリの別フォルダに丸コピー。

### R15. テストとモック

- MVP では手動 E2E（自分で触って確認）で十分。
- クロール処理は外部 fetch があるので、ロジック関数だけ単体テストし、
  実フィードはサンプル XML をリポジトリに同梱する。

---

## やらない（明示的に除外）

- マルチユーザー化／権限制御
- リコメンドのために大きな機械学習モデルを動かす
- クラウドへのホスティング（VPS / Vercel 等）
- SaaS 化

これらは Issue の意図（「自宅で使う／自分用」）と方向が違うので、選択肢から外す。
